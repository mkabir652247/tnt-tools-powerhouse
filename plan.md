# Plan: TNT Tools homepage and catalog loading

## Approved behavior

The homepage renders Categories before Featured Products. Featured Products shows up to eight items initially; “Show more” appends every product not yet displayed after the visible featured items, without restarting the list or duplicating products. “Show less” returns to the initial featured preview. If no products are featured but products exist, shoppers can still expand to browse the full catalog.

Active categories load in their own cached query, so they are usable independently from product images/specifications. The category request is shared with the catalog loader to avoid a duplicate database call. Only active roots and direct active children of active roots are storefront categories/products. A live read-only check found zero currently active children beneath inactive roots and zero active products in those categories. During a category request or an error, the UI does not present seed/demo categories as if they were live links; it shows loading, empty, and error states. The Categories page does not show zero product counts as final while product data is pending or unavailable.

## Performance diagnosis and constraints

On October 22, 2026, the live TNT Tools database reported 42 active products and 4 active categories, with indexes present on `products.is_active`, product/category relationships, and product-image/specification lookups. Supabase EXPLAIN ANALYZE measured the active category query at 0.142 ms and the product query at 0.276 ms on the database; this does not measure the customer's browser-to-API or image-CDN timing. The `product-images` Storage bucket has 62 objects; a fresh live count found 54 unique bucket URLs referenced by active listings and 8 unreferenced bucket objects. The referenced objects were audited at 114,747,660 bytes (about 115 MB), 35 larger than 1 MB, with the largest at 10,250,539 bytes (about 10.3 MB). A live audit found three referenced files over 5 MiB (10.25 MB, 7.99 MB, and 5.39 MB), attached to two products. The previous uploader stored selected files unchanged up to the bucket's 10 MiB limit, and product cards use original URLs, so large image payloads are a confirmed, high-confidence source of slow rendering. Four active categories currently have no database image URL and two active products have no image rows; existing category/product fallback art remains in place.

Optimize every Storage-backed image URL referenced by `product_images` (active and inactive listings) by decoding it, fitting the entire image inside a transparent square with a longest edge of at most 1600 px (never crop or distort, and never upscale), converting to WebP at quality 0.84, uploading a new UUID-named object under the authorized admin's own Storage folder, then updating only its database URL references. After successful upload and an exact reference-count check, delete the source object only when it is larger than 5 MiB; keep smaller sources for rollback and leave external URLs and unreferenced Storage objects alone. New product uploads have a 5 MiB source-file cap and must be square 1:1 within a 5% tolerance; unsupported dimension decoding or out-of-range ratios are rejected before upload. Accepted images are likewise padded into an exact square canvas no larger than 1600×1600 and encoded to WebP. The processed object and the Storage bucket both enforce a maximum of 5 MiB. Continue using immutable cache headers and the same admin-only, own-folder upload permissions.

Supabase's public image-transformation endpoint is disabled for this tenant, so existing-image conversion uses a full-admin-only batch action in the signed-in product panel. It processes unique Storage URLs sequentially, shows progress and total bytes saved, and deletes only originals over 5 MiB after their references are switched and verified unused; originals at or below 5 MiB remain. The action is idempotent for objects it has already converted. Product Sub-admins retain their existing product permissions and cannot run this cross-catalog image maintenance action.

## Implementation and structure

- `src/routes/index.tsx`: Categories-before-Featured order and append-only product expansion.
- `src/lib/catalog.ts`: independent active-category loader alongside the full catalog loader, sharing category data. Database EXPLAIN ANALYZE is sub-millisecond; user-visible latency still needs browser/network measurement because SQL execution time excludes the API and image CDN.
- `src/lib/shop-store.tsx`: category fetch/cache and category-specific loading/error state; no demo-category links during live loading.
- `src/routes/categories.tsx`: clear category loading/error/empty states and pending/unavailable product-count indicators.
- `src/routes/admin/products.tsx`: future uploads enforce file-size/aspect checks; full admins can run the existing-image replacement/removal action with progress and reference-safe cleanup.
- `src/lib/product-image-optimizer.ts` and `src/lib/product-image-batch-optimizer.ts`: browser-side square WebP conversion for strict new uploads and full-admin conversion of existing non-square images.
- `supabase/migrations/20261022124000_limit_product_image_size_to_5_mib.sql`: reduce the existing product-images bucket maximum from 10 MiB to 5 MiB (applied to the live project).
- Keep the TNT Tools design, TanStack Start, React Query, and Supabase stack; change only image URL references after optimized copies upload successfully, and delete only oversized source objects once no database reference remains.
